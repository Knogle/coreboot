# ASRock Rack B565D4-V1L

**Current source snapshot, 2026-11-16:** This local downstream alpha passed
configuration generation for 42 saved profiles and one isolated Cezanne/SeaBIOS
32 MiB host build. It has no current Board regression or reproducibility proof.
Earlier physical results in this document apply to their named historical
images, not this branch. See
[B565_ALPHA_SOURCE.md](../../../B565_ALPHA_SOURCE.md) for the current build
contract and external-input manifest.

Historical test records referenced below live in the separate local
`porting/asrock_am4` evidence archive and are not part of this source alpha.
Paths under `blobs-local` and `.site-local` refer to operator-local evidence
or bench policy and are intentionally absent from this repository.

This is an experimental AM4 port with separately selected Cezanne, Matisse
and Vermeer backends. The SPI device is documented as 32 MiB at 3.3 V.
The normal build uses original signed AMD PSP/ABL/APCB firmware for DRAM
training and builds the x86 coreboot stages and selected payload from source.
It does not call x86 FSP-M or FSP-S. This remains an **alpha**, not a
production-qualified release or automatic vendor-like CPU selection.

The current Vermeer profiles explicitly select the complete original F20
Vermeer ABL and original A21213 microcode inputs. The ABL binary is supplied as
`3rdparty/blobs/mainboard/asrockrack/b565d4_v1l/vermeer-f20-abl.bin` (511680 bytes,
SHA256 `f67f88a0bcf1949dae9c1f74cb9a889e4c645f83d9eb4ebe7bbd36b741862f5a`).
The normal packer checks the whole unit, its twenty stages, four exact routing
directory changes and both firmware banks. A RAW FFS file and padding preserve
complete firmware-volume structure. Both payloads use the larger storage
layout, since the compact payload would overlap this ABL allocation. Keys,
APCB, SoftFuse and fuse policy remain unchanged; the active Vermeer ABL is
deliberately updated, so these profiles do not preserve every original PSP
firmware byte. Default preservation checks remain strict when this explicit
cohort option is disabled.

The later normal main-tree profiles have physical evidence for SeaBIOS87
and EDK2/CSM86, with 319 frozen critical inputs and standard coreboot make.
Both boot the existing SATA Proxmox installation with twelve threads,
32 GiB ECC, default board options, RTC/ACPI checks and two-minute KVM guest
verification. EDK2/CSM86 also warm-boots the existing SATA MBR/GRUB through
its embedded CSM application; that legacy OS has eleven threads because
CSMWrap reserves one BIOS helper. A two-minute KVM guest test and actual
ACPI disassembly pass on that legacy path. The unchanged boot order then
returns to native UEFI with twelve threads after a normal OS reboot.
These are bounded alpha results, not a full cold-start CSM acceptance.

The installed ConnectX-3 VPI card advertises SR-IOV after enabling its
firmware SRIOV_EN setting; the original configuration is preserved. Normal
coreboot PCI allocation reserves the VF BAR range. Linux creates two VFs
in separate native IOMMU groups; one initializes its real mlx4 driver in a
VFIO/KVM guest and passes five minutes of CPU/memory verification while
host MCA/EDAC remains zero. This does not qualify physical network traffic
or DMA throughput. Two early NVMe IOMMU faults in that boot predate the VF
test and remain unresolved; later clean boots do not establish a fix.
The PCI function for CCP remains hidden under the accepted policy.

A longer host/guest test on current normal EDK2/CSM86 is running separately;
it has no final result yet. The planned four 32-GiB ECC modules and a USB
boot medium are currently unavailable. Physical memory qualification still
covers only one 32-GiB ECC UDIMM, without injected correction evidence.
See the current acceptance record for exact boot IDs, archive indexes and
all remaining limits. No image gains a production claim from enumeration
or a successful short test.

### Firmware identification

Use the standard coreboot SMBIOS naming convention. The BIOS vendor is
`coreboot`; system and board manufacturer/product remain `ASRock Rack` and
`B565D4-V1L`. With `CONFIG_LOCALVERSION` empty, SMBIOS Type 0 uses the normal
coreboot build version. Do not append an automatic payload name or add
distribution branding. The configuration, image filename, release manifest
and payload boot output identify SeaBIOS or EDK2.

For the explicitly requested alpha release, the `edk2_alpha` seed uses the
standard `CONFIG_LOCALVERSION` mechanism to expose
`alpha1-94fab62214e6-dirty` in SMBIOS and the coreboot boot banner. The
`edk2_full_alpha` build profile similarly uses `alpha2-94fab62214e6-dirty`.
The combined `edk2_csm` profile uses `alpha7-CSM`, explicitly requested by
the operator, to identify the additional legacy capability in SMBIOS Type 0.
It keeps `coreboot` as BIOS vendor and the actual board manufacturer/product.
Other local alpha profiles also carry their documented explicit version;
the global `CONFIG_LOCALVERSION` default remains empty. The alpha string identifies this local port
revision and is not an upstream coreboot release tag.

Release builds should use normal coreboot version and date generation,
without `BUILD_TIMELESS=1`. That diagnostic setting replaces the version with
`-TIMELESS--LESSTIME-` and the date with `01/01/1970`. The ordinary Git-backed
build derives its version and date from the checkout; an uncommitted tree
retains the `-dirty` marker. The source archive and manifest must identify the
local port changes separately. Do not invent a release tag or board revision.

The physically tested Source23 images were built with `BUILD_TIMELESS=1` and
retain those original strings. This policy does not modify those images or
qualify a new build on hardware. Naming also does not complete the remaining
SMBIOS work: the observed dummy serial number, unset UUID, missing CPU model
string and absent Type 16/17 memory tables remain separate limitations.

### Build dependencies

A normal coreboot cross toolchain is required. Set `XGCCPATH` if the toolchain
is installed outside `util/crossgcc/xgcc`. The host compiler must support the
coreboot checkout's C standard; this workspace uses Clang 19 for host tools.
EDK2 additionally needs NASM and UUID development headers. iPXE's host
compression tool needs the liblzma development headers and library. These
are host build dependencies, not target firmware components.
The full EDK2 profile also needs ImageMagick's `convert` for the splash
bitmap and `iasl` in `PATH` for the RAMdisk driver's ACPI table. The selected
LVGL renderer requires both `LvglPkg` and its nested LVGL submodule; the normal
payload build initializes them recursively.
The UefiPayloadPkg workflow also initializes libspdm when it is present in
the selected EDK2 repository: SecurityPkg exports its include directory even
when no SPDM driver is selected. The library's own test submodules are not
needed for this payload.

This board selects `EDK2_PATCHES_DIR` for the MrChromebox payload. The normal
build applies the board's source patch so an empty disk or missing EFI loader
does not require a key before trying the next boot option. Other load errors
retain their diagnostics. The build keeps owned patch snapshots and removes
them before a subsequent source checkout, preserving unrelated source edits
and preventing the patch from leaking into another board or revision.
Native280 and Native282 physically qualify this automatic continuation through
default-kernel UEFI Linux boot with all four DIMMs. Native283 also boots the
default kernel after holding the diagnostic first missing-loader key wait for
180 seconds. These successes do not establish the cause or repair of the
earlier Native275/277 AHCI-reset MCE.

`B565D4_FADT_COLD_RESET` is disabled by default. The two separate `cf9_reset`
seeds enable the existing Cezanne CF9 decode and complete power-good reset
policy, check the retained register readback, and only then advertise I/O
`0xcf9`, byte value `0x06`, in the FADT. This prepares a future reset without
triggering one during table creation. Both variants build and pass HOST image
and workspace checks; target reset qualification is pending. See the
reset experiment (`../../../porting/asrock_am4/RESET_CF9_20261023.md`; external historical evidence).

The release seeds select coreboot log level 5 and SeaBIOS debug level 3. SeaBIOS
level 8 prints individual xHCI transactions and can add several minutes when
loading a large kernel and initramfs over a 115200-baud console.
The SeaBIOS release seed tries the tested SATA port before the Transcend USB
port. The debug seeds keep the USB device first. Both use SeaBIOS's ordinary
`bootorder` file; adjust it when the disk or port topology changes.

The Memtest seed selects the stock 64-bit Memtest86+ secondary payload and
tries it before the disks. Its Linux boot-protocol command line selects COM2
at 115200 baud. Both 32-bit and 64-bit variants have been built with the normal
workflow; their payload inputs are kept in the selected object directory.

The 64-bit secondary payload has also completed its first default pass on the
board with zero errors. It reported 31.8 GB of testable memory with the two
16 GiB DIMMs, including the two-pattern bit-fade test. Upstream Memtest86+ 6.20
reduces first-pass iterations by three and disables test 1 by default. This
result does not qualify multiple passes, an overnight test, or reserved
firmware-owned memory.

The separate `memtest9` seed pins upstream revision
`e81b268822bd68c4fd700483217061be84cb2841` (9.00). The ordinary payload
workflow supports its `build/x86_64` layout and combined `mt86plus` output,
while retaining the 6.20 layout and binary. This comparison does not change
DRAM training, timings or the retained PSP/ABL/APCB cohort. It does not
establish that the earlier four-DIMM data errors were false positives.
Native279 completes its first shortened default pass over 43.8 GiB with zero
errors. Native284's extended comparison on that same image reports an error
during its second pass: physical address `0x679847170`, bit 54, matching the
earlier 6.20 observation with a different test and pattern. Separate test-3
diagnostics over 25–27 GiB complete ten parallel and two sequential passes
without errors; they do not resolve the full-memory failure. After removal
of the 4-GiB and 8-GiB modules, the unchanged image boots with 31.8 GiB testable
memory, twelve threads and DDR4-2400 at 17-17-17-39. Its new multiple-pass
two-module comparison is pending.

The final image is `build/b565d4-seabios/coreboot.rom`. All x86 coreboot stages
and the selected payload are built from source. The board's `image.mk` uses
ordinary coreboot build dependencies and CBFS intermediates; it does not need
a separate manual packaging command, an old stage ELF, or a `/tmp` source tree.

Use the normal cbfstool to inspect the resulting physical image:

### Full EDK2 profile

The `edk2_full_alpha` seed enables the standard coreboot hare splash and BGRT,
LVGL graphical setup, EFI Shell, serial console, PS/2 and USB input, SATA,
NVMe, SCSI, SD/eMMC, UFS and RAMdisk drivers. FAT, exFAT, ext2/ext4 and NTFS
drivers are included. Network components include IPv4/IPv6 PXE, HTTP/TLS,
iSCSI, VLAN and generic EFI iPXE with its supported NIC drivers. EFI PCI
Option ROM loading is enabled. The board's second owned EDK2 patch connects
the TLS configuration constructor to the existing null QEMU fw_cfg library;
physical hardware has no QEMU configuration channel. TLS trust certificates
must be supplied through the UEFI configuration; the EMU variable store does
not retain them across a reset.

`B565D4_LARGE_PAYLOAD` selects a larger physical raw-FFS body at SPI offset
`0x1a5e000`. It replaces three unused vendor FV_IMAGE files, bounded by
`0x1a5d508` and `0x1d5f4d8`, and mirrors the change in the other bank. The
PSP/BIOS directories, their referenced firmware and the DRAM load addresses
are preserved. The compact default layout remains selected by other seeds.
This is a HOST-built experimental layout; a successful build does not prove
its target boot or graphics output.

The port still selects `NO_SMM` and EDK2's `VARIABLE_SUPPORT=EMU`. Persistent
UEFI settings, protected Secure Boot variables, firmware update capsules and
S3/resume are separate platform work. TPM 1.2/2.0 drivers are included, but
their presence does not establish a working physical TPM, fTPM or PSP service.
Native PXE and HTTP boot also need a bound NIC driver; including the network
stack alone does not qualify a particular adapter. The prior CCP function
visibility policy remains in effect.

### Experimental legacy boot from EDK2

The `edk2_csm` seed retains the full EDK2/ACS profile and enables
`EDK2_CSMWRAP`, which defaults on for this board's qualified large-payload
EDK2 configuration. It can be explicitly disabled. The ordinary coreboot build fetches pinned
[CSMWrap](https://github.com/CSMWrap/CSMWrap) and SeaBIOS sources, builds
`Csm16.bin` and its EFI wrapper, embeds the application in EDK2's firmware
volume, and registers **Legacy BIOS boot (SeaBIOS CSM)** in the boot menu.
Select that entry for a legacy MBR target; ordinary UEFI boot remains available.
The current combined profile is physically installed as `alpha7-CSM`.
Actual SMBIOS Type 0 confirms `coreboot` / `alpha7-CSM`; a fresh ordinary
NVMe UEFI boot uses all twelve threads and registers the built-in legacy
entry. Its entire EDK2 payload and CSM are literal to the preceding physical
legacy Linux and FreeDOS tests. See the
alpha7 combined-profile record (`../../../porting/asrock_am4/CSM_DUAL_BOOT_ALPHA7_20261026.md`; external historical evidence).
This is an EFI application using the genuine Compatibility16 interface,
not a complete implementation of EDK2's historical LegacyBiosDxe protocol.

The BIOS proxy reserves one logical CPU without SMM. A legacy OS therefore
sees eleven threads on the tested Ryzen 5500; an ordinary UEFI boot retains
all twelve. The application refuses entry with Secure Boot enabled. Existing
EMU-variable and platform qualification limits still apply.

Board adaptations move the low stub to `0x40000`, preserve coreboot's reserved
`0x30000`–`0x3ffff` SIPI allocation in E820, and route wrapper and BIOS output
through AST2500 UART2 at `0x2f8`. Linux reinitializes the temporarily disabled
IOMMUs from IVRS. The prior native ACS configuration and CCP visibility policy
remain in effect. Generic DOS memory allocation is not yet qualified.

The initial physical application test booted the existing SATA MBR/GRUB into
Proxmox Linux with EFI runtime absent, eleven CPUs, about 32 GiB, RTC progress,
valid ACPI checksums and 25 genuine IOMMU groups. The two known startup IOMMU
events remain open. The supplied AMI archive was used as a lifecycle reference;
no proprietary AMI source is incorporated in the application.

The ordinary alpha6 CSM build was subsequently flashed, verified and read back
in full. Its embedded application also booted the SATA MBR into Linux, and its
normal NVMe UEFI path then booted with all twelve threads. The actual UEFI boot
variables include the legacy entry. Temporary EFI launchers were removed and
all original EFI files verified. See the
CSM test record (`../../../porting/asrock_am4/CSM_EDK2_20261026.md`; external historical evidence) for image
hashes, complete captures, the one-CPU legacy cost and remaining qualifications.

## Stage and memory contract

The PSP loads the board's compressed reset image into DRAM. The native
bootblock enables the physical UART and follows the ordinary coreboot path to
a separate romstage. Romstage reads APOB, verifies that the selected workspace
lies inside a positively reported available interval, and preserves the
reported exclusions and firmware owners.

| Region | Current placement |
| --- | --- |
| Early CBFS | `09c10000..09c90000` |
| Initial romstage | `09d00000`, at most `0xa0000` bytes |
| Reset vector | `09fffff0` |
| Selected parent workspace | `02000000..02800000` |
| Later read-only CBFS medium | `020d0000..02150000` |
| Bounded CBMEM arena | `02150000..02800000` |

A conflicting APOB allocation causes refusal instead of reclassifying unknown
memory as free RAM. PSP, graphics, firmware, reset-image and other reported
reservations remain separate from allocatable OS memory.

The later 512 KiB CBFS is read through the FCH SPI controller and checked against
its build-generated SHA-256 before use. The ordinary rmodule loader allocates,
decompresses, relocates and clears ramstage BSS inside the bounded arena. Its
size, initialized parameter offset and stored CBFS location are derived from
the actual build outputs. The board admission wrapper must not also be called
from inside the ordinary rmodule loader: that would recursively enter the
single-attempt check.

SeaBIOS reads this reserved DRAM copy with its standard `CBFS_LOCATION` option,
set to the medium's end at `02150000`. The image builder stores the legacy CBFS
master-header pointer as a signed offset from that end, so it remains valid
after copying. The intermediate's absolute flash pointer is not a valid pointer
into the DRAM copy. This CBFS path supplies SeaVGABIOS, boot order, serial console
configuration and optional PCI ROM overrides to the unmodified SeaBIOS source.

Ramstage uses the normal device/resource, table and payload phases. The selected
payload is encoded by cbfstool as SELF, loaded through the genuine coreboot
SELF loader and entered through the normal architecture handoff. The current
flash source for the payload is a board-specific raw FFS file; this preserves
space in the later CBFS. Payload segment sizes and decoded checksums are
generated from the selected payload rather than assuming an EDK2-only layout.

## Serial and graphics

The physical COM header uses AST2500 UART2, logical device 3, at I/O `0x2f8`,
115200 baud, 8N1, divisor 1, IRQ 3. The colliding Nuvoton UART decodes are
disabled. The board diagram's UART1 label does not match the qualified routing.
The ASPEED RTS pad configuration is part of the board initialization.

For Linux serial output, use `console=ttyS1,115200n8`; an early console can use
`earlycon=uart8250,io,0x2f8,115200n8`. A kernel configured only for COM1 can boot
successfully while producing no Linux text on this physical connection.
Replace inherited COM1 parameters when configuring an installed operating
system. Appending COM2 after an existing `console=ttyS0` still selects the first
serial console, as described in the
[Linux serial console documentation](https://docs.kernel.org/admin-guide/serial-console.html).

For GRUB, select the I/O port explicitly:

```text
serial --port=0x2f8 --speed=115200 --word=8 --parity=no --stop=1
```

SeaBIOS places the sole detected UART, at `0x2f8`, in the first BIOS data-area
COM slot. GRUB's `--unit=1` then refers to an empty slot. The explicit port has
been tested with both BIOS and UEFI boots of the installed Proxmox system.

The optional graphics configuration uses the existing `DRIVERS_ASPEED_AST2050`
driver, which also supports the installed AST2500 revision. SeaBIOS uses the
built SeaVGABIOS against the coreboot framebuffer. EDK2 uses its coreboot
framebuffer Graphics Output Protocol driver. This does not require an Intel
GOP/VBT blob. Firmware framebuffer/GOP initialization and an observed picture
on a connected display are separate test claims.

## PCI and boot policy

The test bench includes an I340 with four `8086:150e` functions, onboard I210
`8086:1533`, SAS2308 `1000:0087`, a TP-Link WiFi card and an ASMedia USB card.
The optional iPXE configuration builds the I210 ROM through coreboot's normal
external iPXE target and adds it to CBFS. Change the PXE PCI ID for a different
network device. Building an iPXE ROM alone does not establish network boot.
The SeaBIOS seeds use the BIOS console for iPXE, with SeaBIOS serial redirection,
to avoid interleaving it with iPXE's direct serial output.

The EDK2 iPXE seeds select `IPXE_EFI_DEVICE_SPECIFIC` and PCI ID `8086,1533`.
This uses the ordinary external iPXE target to build a smaller EFI image for
the I210. The generic EFI image includes many unrelated network drivers and
does not fit this board's current payload allocation with the selected EDK2
features. The image builder checks that allocation and refuses an oversized
payload. The EFI seeds use the EFI console for iPXE input and output.

`B565D4_SKIP_SAS_OPROM` provides an empty `pci1000,0087.rom` override for SeaBIOS.
It suppresses only the adapter's legacy boot ROM; the PCI function, BARs and
Linux mpt2sas initialization remain enabled. The supplied SeaBIOS test seeds
select this option after the optional legacy ROM delayed the first normal
build's boot. Native graphics and explicitly supplied network ROMs remain
available. Direct SAS legacy boot is a separate qualification task.

The configuration seeds select power-on after AC restoration. The bench must
still measure the actual state: a previous image can leave a different
power-failure policy active until the new bootblock first executes.

## Four DIMMs and x16-slot bifurcation

### ASPM and IOMMU test profile

The `*_pcie_power_iommu` seeds enable negotiated ASPM and use the regular AMD
IOMMU resource driver, IVRS table generator and root-bridge `_OSC` method.
EDK2 Alpha4 physically boots NVMe Linux with interrupt remapping enabled.
A short policy/idle/direct-read test confirms L1 switching for NVMe and the
I210 link; the LSI link has no common L0s/L1 mode and remains disabled.

In the Alpha4 profile the groups are too coarse for independent LSI assignment:
LSI, management NIC and boot NVMe share group 1. An actual QEMU/VFIO assignment
attempt is rejected as `group 1 is not viable`; no successful device assignment
or isolation is claimed. There is also one retained early IOMMU
`INVALID_DEVICE_REQUEST` event, with no increase during these tests. The
current cards expose no SR-IOV VFs. See the
ASPM/IOMMU/VFIO test record (`../../../porting/asrock_am4/ASPM_IOMMU_VFIO_20261026.md`; external historical evidence)
for exact scope and remaining issues. The SeaBIOS variant is HOST-built only.

### Native Cezanne ACS test profile

The `*_acs` seeds enable the default-off `B565D4_PCIE_ACS` option. The board
applies the same-board Cezanne BaseRn NBIF straps and seven ACS DXIO parameters
per wrapper before link training. No Linux ACS override or kernel patch is
used. Alpha5 ACS physically improves Linux grouping from five to 25 groups;
the CPU-attached WLAN and boot NVMe have separate groups. The WLAN card runs
with its real driver in a KVM guest, including passive scans, MSI interrupts,
simultaneous verified host/guest load and ASPM policy changes.

The Promontory branch still shares a twelve-function group, including LSI and
the management NIC. Independent LSI assignment remains rejected by VFIO. One
early AMD-Vi `INVALID_DEVICE_REQUEST` remains unresolved. The SeaBIOS/SATA
boot also has one NVMe `IO_PAGE_FAULT` during Linux probe; subsequent direct
read comparisons pass, but its cause remains open. Both payloads physically
produce the same 25 groups. This is an experimental profile with qualified
functionality and explicit limits, not a general DMA-isolation or arbitrary
passthrough guarantee. See the
native ACS test record (`../../../porting/asrock_am4/ACS_NATIVE_20261026.md`; external historical evidence).

### Persistent PCIe slot configuration

`B565D4_PCIE_RUNTIME_OPTIONS` enables the standard coreboot CMOS option API
and describes `pcie_slot_bifurcation` using both `cmos.layout` and CFR. The
board reads it before constructing and training the CPU-slot DXIO descriptors.
The existing AMD Jaguar board's option API/CFR approach is the reference.

| Stored value | Selection |
| --- | --- |
| 0 | Default: use the build-time lane configuration |
| 1 | x16 |
| 2 | x8/x4/x4 |
| 3 | x4/x4/x4/x4 |

Both supplied runtime seeds default to four x4 groups. Invalid values fall
back to the build-time selection. The allocation-only probe is unavailable
in runtime-option builds and cannot be selected through the saved values.
Apply a full power cycle after saving a new lane configuration.

The SeaBIOS seed includes the ordinary `nvramcui` secondary payload. Its
`pcie_slot_bifurcation` field uses left/right arrows; F1 saves and requests a
CF9 reboot. EDK2 exposes the setting under `Platform Setup Menu` →
`PCI Express` → `CPU x16 slot lane configuration`. Its CFR driver uses the
coreboot CMOS layout to read and save this numeric option. CMOS is the shared
persistent backend; this does not turn the existing EMU EFI variable store
into persistent storage or enable SMMSTORE.

The board owns only CMOS byte `0x60` and its big-endian additive checksum at
`0x61..0x62`. RTC registers, the century byte, the boot counter and AMD's
reserved tail are excluded. The image builder puts identical layout/default
files in the PSP-loaded early CBFS and the later verified medium. ROMstage
defers layout lookups through `cmos_option_table_ready()` until that later
medium is loaded; its earlier console queries use their usual fallback.

Both x16 and four-x4 were physically applied with SeaBIOS and EDK2. SeaBIOS
used stock `nvramcui`; EDK2 saved through the public HII route into the normal
CFR handler and reloaded the values on successive full cold starts. The final
EDK2 four-x4 boot used the restored original NVMe loader and reached Linux
with NVMe Gen3 x4, 32 GiB, twelve threads, advancing RTC, zero MCG status and
valid ACPI tables. Temporary EFI diagnostic loaders were fully restored.
The graphical LVGL browser was not visually observed, and there is no installed
x16 endpoint for traffic qualification. See the
runtime option record (`../../../porting/asrock_am4/RUNTIME_PCIE_OPTIONS_20261026.md`; external historical evidence)
for the exact test sequence, image hashes, remaining limits and saved evidence.

### DIMM and earlier lane qualification

The four-DIMM comparison uses two 16-GiB DIMMs, one 4-GiB DIMM and one 8-GiB DIMM
installed together. Both normal SeaBIOS and normal EDK2 builds have booted
Proxmox with twelve threads and this 44-GiB topology. A PCIe NVMe SSD in the
operator-declared third x4 lane group enumerates below root port 00:02.4 at

## Manufacturer reference

The ASRock Rack *B565D4-V1L/25 User Manual*, version 1.0 (May 2021), provides
the board block diagram on printed page 11 and the electrical slot widths on
page 20. PCIE6 (x16) and PCIE4 (x4) connect to the CPU; PCIE5 and PCIE3 (both
x4) connect through PRO565. The diagram also identifies the AST2500, I210-AT
and NCT6796D-R connections. Link generation still depends on the installed CPU.

Printed page 41 documents OS-controlled RTC alarm wake and PCIe wake. Pages
49–50 list slot-6 lane width, L1 substates, CLKREQ and PME wake settings. These
are useful references for the manufacturer's intended behavior, rather than
qualification of those functions in this port. The manual contains no FCH
register map or description of the separate ASMedia expansion card.
