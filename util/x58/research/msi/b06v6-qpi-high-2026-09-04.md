# B06V6 vendor-assisted QPI High transition

> **2026-09-04 RTC-bank erratum:** this transition and its QPI endpoint state
> remain valid. Values below labeled extended CMOS were obtained while ICH10
> U128E was clear and were therefore standard RTC clock/calendar bytes reached
> through aliased ports `0x72/0x73`. They are not reusable policy inputs; B06V9
> replaces that interpretation with a deterministic wrapper-state profile.

## Evidence boundary

This record covers one live MSI X58 Pro-E experiment on 2026-09-04.  It
establishes that the extracted MSI CSI path can stage both ends of QPI link 0
and that the documented IOH CPU-only reset makes the link enter its operational
speed.  It does not establish a native coreboot QPI implementation, a completed
third CSI call, High-QPI memory initialization, or a ramstage handoff.

The relevant public register definitions are in the
[Intel 5520/5500 IOH datasheet](https://www.intel.com/content/dam/www/public/us/en/documents/datasheets/5520-5500-chipset-ioh-datasheet.pdf):

- `IOH.SYRE.CPURESET` is device `00:14.2`, offset `0xcc`, bit 10;
- the IOH QPI physical link-0 function is `00:0d.0`;
- its extended physical-layer registers include `PH_CTR` at `0x82c`,
  `PH_PIS` at `0x840`, `PTV` at `0x854`, and `PRT` at `0x864`;
- `00:14.1:0x7c/0x80` are sticky firmware scratchpad registers `SR0/SR1`.

## Why CF9 was the wrong reset

The first attempt staged the same High-QPI state and then issued ROMMON
`reset init`, implemented as CF9 `00 -> 04`.  No reset-vector or serial output
followed; AC removal was required.  This is not evidence that CSI staging
failed.

Static analysis subsequently found two copies of the actual MSI choreography:

1. loaded CSI calls its own helper, which toggles `IOH.SYRE.CPURESET` and
   enters a `CLI/HLT` fail-stop when an internal reset is required;
2. the outer MSI caller handles CSI return `EAX=1` by persisting its phase,
   clearing `SYRE.CPURESET`, clearing `SR0/SR1`, emitting POST `fe`, setting
   `SYRE.CPURESET`, and entering a `CLI/HLT` fail-stop.

The Intel datasheet independently describes `SYRE.CPURESET` as the mechanism
that resets the CPUs and only the CPUs.  Therefore CF9 `00 -> 04` must not be
used as the X58 QPI transition trigger.

## Successful transition

After true AC removal, B06V6 entered `COLD_DEFAULT`.  Initial QPI state was:

```text
CPU ff:02.1:50 = 160c0110
CPU ff:02.1:54 = 00000010
CPU ff:02.1:80 = 030f0f03
IOH 00:0d.0:82c = 00006020
IOH 00:0d.0:840 = 030f0f03
IOH 00:14.2:cc = 00000200
```

The first armed `vcsi 0` did not return.  Its internal MSI
`SYRE.CPURESET` path reset the CPU, after which the reset vector, bootblock,
romstage, and CAR ROMMON all returned with retained I801 state.

The second `vcsi 0` returned:

```text
EAX=00000001 EBX=00000000 ECX=000002a6
EDX=fff8fcd8 EDI=fff8fcd8 EFLAGS=00000086
CSI_FNV=92e228e7
```

Disassembly shows that `ECX=0x2a6` is a composite progress/reset-reason mask,
not an error checkpoint.  `EAX=1` is the outer caller's CPU-reset-required
case.  The paired pre-reset state was:

```text
CPU ff:02.1:50  = 160c0110
CPU ff:02.1:54  = 00000012
CPU ff:02.1:6c  = 0040a0a0
CPU ff:02.1:80  = 030f0f03
CPU ff:02.1:94  = 00010202
CPU ff:02.1:9c  = 00000502
CPU ff:02.1:a0  = 00000c00
CPU ff:02.1:a4  = 00322808
IOH 00:0d.0:82c = 004060a0
IOH 00:0d.0:840 = 030f0f00
IOH 00:0d.0:854 = 00010102
IOH 00:0d.0:85c = 00000002
IOH 00:0d.0:864 = 00322808
```

This proves that CSI staged the CPU and IOH endpoints together.  Values that
appear only after reset must not be replayed as pre-reset writes.

The live experiment then reproduced the outer MSI sequence.  The existing
low-six policy bits were preserved while phase 1 was written as the
complemented pair `EXT88/89=67/98`.  With every write individually armed, the
reset sequence was:

```text
00:14.2:cc <- 00000200       # clear CPURESET bit 10
00:14.1:7c <- 00000000       # SR0
00:14.1:80 <- 00000000       # SR1
POST 0xfe
00:14.2:cc <- 00000600       # set CPURESET bit 10
```

The final configuration write interrupted the ROMMON acknowledgement.  The CPU
immediately re-entered the B06V6 reset vector, bootblock, romstage, and CAR
ROMMON.  The resulting link state was:

```text
CPU ff:02.1:50  = 160c0112
CPU ff:02.1:54  = 00000012
CPU ff:02.1:6c  = 0040a0a0
CPU ff:02.1:80  = 070f0f03
CPU ff:02.1:94  = 00010202
CPU ff:02.1:9c  = 00000502
CPU ff:02.1:a0  = 00017600
CPU ff:02.1:a4  = 00322808
IOH 00:0d.0:82c = 004060a0
IOH 00:0d.0:840 = 070f0f03
IOH 00:0d.0:854 = 00010102
IOH 00:0d.0:85c = 00000002
IOH 00:0d.0:864 = 00322808
CPU link ff:02.0:50 = 86000000
CPU link ff:02.0:58 = 00064555
IOH link 00:10.0:c8 = 0606fc00
```

The decisive operational-speed indicators are the PLL-status change
`160c0110 -> 160c0112` and both endpoint `PH_PIS` values changing from
`030f0f03` to `070f0f03`.  They match the stable vendor-High reference tuple.
The link carried reset-vector fetches and sustained the serial CAR monitor.

Thirty-two consecutive CPU `PH_PIS` reads and thirty-two consecutive IOH
`PH_PIS` reads were all `070f0f03`.  A complete 256-byte SPD double-read also
succeeded after the transition.  No DRAM access or MINIT call was made in this
High-QPI state.

## Follow-up reset result

The first successful reset preserved an invalid low-six cookie policy
(`EXT88=0x67`, low six bits `0x27`).  Before a third CSI call, it was corrected
to phase 1 plus policy 1: `EXT88/89=41/be`.  Because generic CMOS writes mark
the current ROMMON vendor context dirty, an additional experimental
`SYRE.CPURESET` was attempted to obtain a clean context.  That second reset at
already-active High QPI did not return serial output and required another AC
recovery.

This follow-up failure does not invalidate the successful Slow-to-High
transition.  It shows that an extra reset is not a safe substitute for entering
the first pass with a correct policy cookie.  A future build must establish
policy 1 before pass 1, carry an explicit one-shot phase/retry guard, and use
the single original MSI caller reset.  Its first High-QPI milestone should run
the third CSI pass and stop in CAR ROMMON; MINIT and ramstage remain separate
later experiments.

## Later AC-cold reproduction and retained-input drift

A later true AC-cold B06V6 run on 2026-09-04 completed CSI's first internal
CPU-only reset and re-entered the reset vector with the expected B06V6 I801
signature.  The second automatic call returned normally with
`EAX/EBX/ECX=2/2/00000106`, failed the exact acceptance gate, and stopped in
CAR ROMMON without invoking MINIT or requesting another reset.

This run captured a useful partial state.  The ordinary link functions already
reported the operational-looking values observed in the High-QPI history:

```text
CPU ff:02.0:50 = 96000000
CPU ff:02.0:58 = 00064555
IOH 00:10.0:c8 = 0606fc00
```

However, both physical endpoints remained unequivocally Slow:

```text
CPU ff:02.1:50/54/6c/80 = 160c0110/00000010/0000a020/030f0f03
CPU ff:02.1:94/9c/a0/a4 = 00000102/00000502/00000c00/001d2c03
IOH 00:0d.0:82c/840     = 00006020/030f0f03
IOH 00:0d.0:854/85c/864 = 00000102/00000002/00322808
IOH 00:14.1:7c/80       = 00000000/00000000
IOH 00:14.2:cc          = 00000600
```

Therefore the ordinary link-function values alone are not a High-QPI success
criterion.  Both physical `PH_PIS` values and the complete paired endpoint
tuple must be checked.

The battery-backed wrapper inputs had also drifted from the successful tuple:

```text
observed after AC-cold: EXT80/81/82/88/89 = be/19/f7/6f/ca
successful input:      EXT80/81/82/88/89 = b3/19/d7/67/cb
```

No claim is made about what changed these bytes.  The result justifies B06V8's
read-only exact-input gate before every vendor call.  After all automatic work
had stopped, ROMMON writes restored the successful five-byte tuple and the
isolated B06V8 cold authorization `CMOS0E=2c`; every byte was read back, and no
further CSI or MINIT call was issued.  The next true AC-cold entry must still
revalidate all values rather than assuming retention.
