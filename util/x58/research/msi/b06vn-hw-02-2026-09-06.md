## Proven path

The retained execution used CPU-A0 `0x00017800`, CPU `9c=0x00a00502`, CSI
raw/canonical hashes `0x03e3d24e/0x908dabb6`, and returned from MINIT with
`EAX=0`. The hard return gate passed. The complete low-memory test and both
complete 8-MiB uncached windows passed, CBMEM was created, the version-9
handoff was verified, and coreboot entered postcar and real ramstage.

B06VN then measured the three X58 PCIe root ports before making any link-start
write:

```text
00:01.0  SPEED=1 WIDTH=0  LT=0 DLLA=0
00:03.0  SPEED=1 WIDTH=16 LT=0 DLLA=1
00:07.0  SPEED=1 WIDTH=0  LT=0 DLLA=0
```

Thus the Radeon slot's root link was already active at Gen1 x16. B06VN
correctly skipped its conditional `0x000c` write to `00:03.0+0x190` and
reported `IOU0 link ready after 0 polls (start-write=0)`. This proves an active
physical/data-link layer, not endpoint configuration visibility.

Coreboot still received `0xffffffff` for the expected downstream function
`01:00.0`; therefore it followed the intended fail-soft serial path. SeaBIOS
later confirmed `No VGA found`. No AMD PCI identity, physical Radeon VBIOS
execution, or graphical output is claimed.

The rest of the payload path did run:

```text
[PAYLOAD] SeaBIOS SELF image loaded
[PAYLOAD] entering SeaBIOS payload
SeaBIOS (version rel-1.17.0-0-gb52ca86e)
PCI device 02:00.0 (vd=10ec:8168 c=0200)
Running option rom at c000:0003
iPXE (https://ipxe.org) 02:00.0
Press Ctrl-B to configure iPXE (PCI 02:00.0)
```

iPXE also completed PCIBIOS and PMM calls and obtained its requested RAM
blocks. The retained trace ends after its first logged SeaBIOS INT 16h `AH=01`
keyboard-status call. A subsequent exclusive 20-second UART capture received
zero bytes, and late Ctrl-B/CR input produced no response. This supports, but
does not prove, a stall in or immediately after the INT 16h path. Ethernet
link, DHCP, TFTP, storage boot, and an operating-system boot remain unproven.

## Newly exposed IOH routing defect

SeaBIOS enumerated 98 functions. In addition to the real RTL8168 at
`02:00.0`, it found 32 aliases with matching vendor/device/class tuples for
the X58 internal functions
`00:0d.0..00:16.7` at `02:0d.0..02:16.7`.

Intel X58 datasheet section 17.6.5.12 documents `IOHBUSNO` at
`00:14.0+0x10a`: with bit 8 clear, the IOH claims its internal device/function
numbers under any bus number; with bit 8 set, it claims them only under the
bus in bits 7:0. The B06VN alias set is the documented bit-8-clear behavior.
This is a known configuration-routing defect, but it is not yet proof that the
same defect hides `01:00.0` because bridge routing may take precedence for that
device number.

A read-only vendor-firmware reference capture measured:

```text
00:14.0 IOHBUSNO 10a.w=0100
LCFGBUS base/limit 11c.b/11d.b=00/fb
GCFGBUS base/limit 134.b/135.b=00/fb
01:0d.0=absent, 02:0d.0=absent, 03:0d.0=absent
```

The same comparison exposed another real but separate missing root-port setup
step. B06VN reads root `00:03.0 LNKCAP=0x00393c42`, whose Maximum Link Width
field is x4, while the vendor-initialized board reads `0x00393d02`, or x16.
The vendor state uses x4 on `00:01.0` and x16 on `00:03.0`/`00:07.0`, matching
the board topology. Intel documents this capability field as BIOS-initialized
RWO state. Because B06VN's live `LNKSTS` nevertheless reports a trained x16
link, the stale advertised capability is not yet proven to cause the missing
endpoint. It must remain read-only in the IOHBUSNO experiment and be tested in
a separate build if the corrected routing still leaves both endpoint reads
absent.

The next isolated experiment should therefore read, conditionally program,
and require `IOHBUSNO=0x0100` before downstream scanning, with before/after
alias probes. The current configuration also has
`CONFIG_NO_ECAM_MMCONF_SUPPORT=y`: coreboot's generic bridge scan probes the
new secondary bus through CF8/CFC, whereas B06VN's link telemetry uses direct
ECAM. A custom read-only scan callback should compare one `01:00.0` identity
read through each mechanism immediately after programming the bridge bus
numbers. That separates a configuration-access/routing failure from genuine
endpoint absence without another device reset. Only if `IOHBUSNO=0x0100` and
both access methods still show absence should a separate build test a bounded
secondary-bus hot reset.
