## Capture integrity

The first start-immediate attachment encountered the already-running payload's
large ANSI stream and was rejected as transport evidence.  It was not imported
into the repository.  For HW-02 the capture process held both `TIOCEXCL` and a
cooperative lock, waited for a measured 0.5-second quiet interval during the
one-second relay interruption, discarded 2,693,486 pre-gate bytes, flushed the
input queue, and stored only the following boot.

Retained artifacts:

```text

```

The metadata records 66,204 raw bytes over 1,155.822888133 seconds, or
57.2786719 bytes/s in aggregate.  This is within the 115200-baud 8N1 envelope;
the rate policy passed.  The raw file contains 1,069 lines.  Its derived RLE
view contains 1,041 runs and names the raw SHA-256 as its source.  The capture
ended one second after matching `enter handle_16:`.  This marker policy means
the evidence ends after that entry; it does not by itself prove the machine
could never return from it.

The discarded pre-gate bytes arrived over 22.384 seconds, an average of about
120,331 bytes/s or 10.45 times the physical 115200-8N1 limit.  They therefore
contain upstream replay or backlog.  Quiet gating and flushing separate them
from the retained coherent execution, but the retained capture has only an
aggregate rate check, not per-chunk timestamps; it cannot prove the absence of
every short local replay burst.

## IOHBUSNO causal result

Immediately before the sole new B06VO write:

```text
[IOHCFG] PRE IOHBUSNO=0000 LCFGBUS=00-00 GCFGBUS=00-ff
         ALIAS01:0d.0=343a8086 ALIAS02:0d.0=343a8086
```

The exact 16-bit `0x0100` store was accepted:

```text
[IOHCFG] POST IOHBUSNO=0100 LCFGBUS=00-00 GCFGBUS=00-ff
          ALIAS01:0d.0=ffffffff ALIAS02:0d.0=ffffffff
[IOHCFG] B06VO IOHBUSNO exact gate PASS (write=1)
```

The later complete SeaBIOS scan found 68 functions through bus 2, rather than
B06VN's 98.  Bus 2 contained only the real RTL8168 at `02:00.0`; none of the
known 32 X58 internal-function aliases at `02:0d.0` through `02:16.7` was
enumerated.  An independent tuple comparison found all 66 common BDF/vendor/
device/class entries unchanged.  The exact count transition is the removal of
32 aliases plus the addition of the two Radeon functions.  Together with the before/after reads and
B06VO's one-write delta, this directly establishes the alias correction and is
strong causal evidence that missing `IOHBUSNO.Valid` programming also blocked
the prior Radeon configuration route.  One run with a different admitted A0
state is not strict proof of the latter until repeated.

The read-only B06VO observation `LCFGBUS=00-00` differs from the vendor
reference's observed `00-fb`, but the Radeon became accessible without
changing it.
Consequently this run supplies no basis for an LCFGBUS write.

## PEG and Radeon result

Root `00:03.0` was already Gen1 x16 with `DLLA=1` and `LT=0`; as in B06VN,
the conditional BIF/start write was skipped.  Its Link Capability still
reported the inherited x4 encoding, but that mismatch did not prevent the
real negotiated x16 link or endpoint access in this run.

After the generic bridge code assigned secondary bus 1, all four paired reads
agreed immediately and remained stable:

```text
T_US=0      BUS=01 CF8=68f91002 ECAM=68f91002 MATCH=1
T_US=1000   BUS=01 CF8=68f91002 ECAM=68f91002 MATCH=1
T_US=10000  BUS=01 CF8=68f91002 ECAM=68f91002 MATCH=1
T_US=100000 BUS=01 CF8=68f91002 ECAM=68f91002 MATCH=1
```

Coreboot accepted `01:00.0` as `1002:68f9`, class `030000`, header `80`, set
VGA forwarding on root `00:03.0`, and assigned these principal resources:

```text
BAR0 prefetchable memory  d0000000-dfffffff  (256 MiB)
BAR2 memory               cff00000-cff1ffff  (128 KiB)
I/O BAR                   f000-f0ff          (256 bytes)
ROM BAR                   cff20000-cff3ffff  (128 KiB window)
```

SeaBIOS additionally enumerated the card's `1002:aa68` audio function at
`01:00.1`.

## Physical VBIOS and payload result

No AMD image exists in CBFS.  SeaBIOS mapped the physical ROM BAR, found a
valid `AA55` image of 117 sectors (59,904 bytes), copied it to `0x000c0000`,
and entered it:

```text
Copying option rom (size 59904) from 0xcff20000 to 0x000c0000
Checking rom 0x000c0000 (sig aa55 size 117)
Running option rom at c000:0003
```

Subsequent SeaBIOS execution configured serial split mode using the installed
VGA BIOS vector, enabled its VGA text console and continued into USB and disk
initialization.  That continuation proves return from the physical VBIOS.  The
operator then reported visible display output during the live run.  No photo
or exact screen contents were retained, so that physical observation remains
operator-reported rather than part of the UART artifact.

SeaBIOS later executed the embedded RTL8168 iPXE ROM and satisfied its PCIBIOS
and PMM requests.  The retained trace reaches its Ctrl-B prompt and first
logged INT 16h `AH=01` entry.  A later post-capture Ctrl-B followed by Ctrl-B/CR
produced no UART output; it may have missed the short prompt and is an operator
observation not retained as a separate capture.  The log also records an i8042
flush timeout and no detected ATA devices.  No Ethernet-link, DHCP, TFTP,
storage or OS-boot result is claimed.

## Conclusion and next boundary

B06VO is the first retained run to prove all of the following in one execution:

1. guarded MINIT return and complete bounded RAM tests;
2. coreboot postcar and ramstage;
3. correct X58 internal-device routing on the enumerated buses 0 through 2
   after `IOHBUSNO=0x0100`;
4. stable CF8 and ECAM visibility of the Radeon over the existing Gen1 x16 link;
5. coreboot PCI resource assignment and VGA forwarding;
6. SeaBIOS execution and return of the card's physical onboard VBIOS;
7. operator-observed display output;
8. continued SeaBIOS execution and RTL8168 iPXE entry.

The PCIe/GPU problem exercised by B06VN/B06VO is therefore solved for this
single run and fixed hardware configuration.  The next observed boundary is
payload progress beyond the first iPXE keyboard-status call; the retained
marker-limited trace does not establish a hang there.  A longer capture must
resolve that boundary before changing IRQ or input policy.  It is independent
from IOHBUSNO and PEG: B06VO has only one complete hardware run, does not
satisfy the required 10-cold/10-warm repetition policy, and has not yet booted
a device or operating system.
