## Exact stop and root-cause boundary

The last state line is:

```text
[SATA] B06VV PCS_PRE ... CMD=0000 ... BAR5=cfcff000 MAP=0060 PCS=0000 ...
SCLKCG=00000000 ... SIZE=800 ... POLICY_CMD=0003 F5_ID=ffffffff
[SATA] B06VV rejected corrected-route/resource/PCS prestate
```

Terminal POST `0x63` is the B06VV failure code.  No B06VV write had yet run:
POST `0x5e`, the first PCS-write boundary, was not emitted.  This makes the
failure safe and diagnostic.

The hardware tuple itself is the intended quiescent AHCI prestate.  The new
information is `POLICY_CMD=0003`: while storing the function's assigned BARs,
the generic PCI resource path selected both `PCI_COMMAND_IO` and
`PCI_COMMAND_MEMORY` because the AHCI function still exposes legacy I/O BARs
0 through 4 in addition to BAR5.  B06VV deliberately requires the software
enable policy to be memory-only before it programs and verifies BAR5.  Thus
the gate rejected coreboot's in-memory future command policy, not a bad
hardware command register, BAR, route, PCS or clock value.

The narrow successor hypothesis is to require this exact observed
`0003` software prestate, clear only `PCI_COMMAND_IO` in the in-memory device
policy, prove the hardware command register remains zero and the policy reads
exactly `0002`, and only then enter the unchanged B06VV PCS/SCLK and B06VW
MEM-only AHCI path.  That operation writes no hardware register.  The later
generic resource-enable phase should consequently preserve MEM-only decode.

## Explicit nonclaims

This run did not reach PCS or SCLK programming, AHCI MMIO, USB admission, ACPI
table publication, SeaBIOS load/entry, the physical Radeon VBIOS, iPXE, a SATA
device, USB input or an operating system.  It counts as one B06WC hardware
execution and zero independently proven electrical-G3 repetitions.  A single
successful memory/QPI run is not ten-run stability evidence and the memory
initialization remains locally vendor-assisted.
