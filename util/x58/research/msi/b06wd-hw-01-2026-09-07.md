## B06WD SATA hypothesis result

The intended software-only correction passed exactly once.  Coreboot changed
its in-memory policy from `0003` to `0002` while reporting no hardware-command
write:

```text
[SATA] B06WD POLICY_CMD 0003->0002 HARDWARE_CMD=0000 HARDWARE_WRITE=0
```

The inherited stages then reached their exact ready gates:

```text
[SATA] B06VV corrected route + PCS + SCLKCG READY
[AHCI] B06VW READY; dynamic ABAR decoded MEM-only, AE=1, PI=3f; SeaBIOS owns HBA reset, BME and every port operation
```

The detailed log shows ABAR `cfcff000`, `PCS=203f` after sampling,
`SCLKCG=00000193`, `GHC.AE=1`, `PI=0000003f`, no HBA reset and no BME.  Port
presence bits sampled as `20`; no IDENTIFY, block I/O or attached-disk success
was attempted or proved before the later ACPI stop.

## Keyboard and USB result

The ICH10R KBC-decode write itself passed: `LPC_EN 2001 -> 2401`, and port
`0x64` changed from open-bus `ff` to `00`.  The subsequent protocol did not
produce a usable keyboard:

```text
[INPUT] B06WD KBC_DECODE 2001->2401 PORT64=ff->00 WRITE_MASK=0400
Keyboard Interface test failed: 0x3
Keyboard reset failed ACK: 0xff
[INPUT] B06WD bounded PS2 probe returned AUX=0; inspect keyboard ACK/BAT log; PNP0303/FADT8042 admission READY
```

Therefore this run proves the decode/readback and bounded return, but it
**does not prove PS/2 input**.  No keyboard ACK, BAT or accepted key action was
observed.

Both EHCI functions and all six UHCI functions were structurally enumerated
and passed the read-only USB admission logic.  The electrical summary was:

```text
[USB-ADMIT] ELECTRICAL EHCI CCS=000 PE=000 OCA=fff OCC=fff UHCI CCS=000 PE=000 OCA=fff OCC=fff CLASS=OC_NO_CONNECT
[USB-ADMIT] B06WC-USBADMIT1 READY STRUCTURAL=PASS ELECTRICAL=CLASSIFIED MUTATIONS=0
```

This is not USB-keyboard success.  The run has no connected/enabled endpoint,
no SeaBIOS USB trace and no accepted USB key action.

## Terminal ACPI boundary

Coreboot reached ACPI table construction after device finalization.  The log
records FACS construction, a native-minimal FADT/FACP addition and an SSDT
addition.  It then stopped before emitting an MCFG entry:

```text
[ACPI] B06WC-ACPI1 FADT NATIVE_MINIMAL=1 SCI_EN=1 SMI_CMD=00000000 PM1_EVT=0500 PM1_CNT=0504 PM_TMR=0508
ACPI:    * FACP
ACPI: added table 1/32, length now 44
ACPI:    * SSDT
ACPI: added table 2/32, length now 52
[ACPI] B06WC-ACPI1 MCFG_GATE PCIEXBAR=ffffffff:ffffffff HOST=34058086 COREBOOT_ACCESS=CF8_CFC
[ACPI] B06WC-ACPI1 FAIL reason=PCIEXBAR
```

Source inspection at the tested commit identifies this as a firmware
false-negative, not evidence that PCIEXBAR or the X58 link was lost.  The ACPI
gate in `acpi_tables.c` reads offsets `0x50/0x54` from `PCI_DEV(0, 0, 1)`, or
`00:00.1`.  The X58 SAD device used by the already-passed platform gates is
`PCI_DEV(0xff, 0, 1)`, or `ff:00.1`, where the expected pair is
`00000000:e0000001`.  After `IOHBUSNO=0100`, the wrong bus-zero alias returns
`ffffffff`, while the direct ECAM read at `e0000000` still returns the exact
X58 host ID `34058086`.

The smallest successor should retain the fail-closed MCFG validation but read
the SAD ID and PCIEXBAR pair from `ff:00.1`.  Omitting MCFG is not required by
this observation.  This proposed source correction is not part of the B06WD
hardware result documented here.
