# Live ICH10R I801 and SPD reference capture — 2026-08-31

## Scope and evidence boundary

The user identified `root@192.0.2.203` as an identical MSI X58 Pro-E
reference system and authorized register-level investigation.  This capture
was made from an already-running PartedMagic/Linux session after vendor
firmware had initialized the platform.  Its boot type was not controlled.
The host reported an Intel Xeon E5645 and the same boot ID as the earlier
2026-08-04 vendor-state work.

Therefore these values are a **verified-hardware runtime reference**, not a
measurement of ICH10R reset state and not evidence of the values seen by B05
before DRAM.  No memory-controller, QPI, EEPROM-data, PCI-configuration, or
SMBus pin register was written during this capture.  Normal Linux I801
transactions were performed through `/dev/i2c-0`.

## I801 controller

Targeted PCI configuration reads found:

```text
BDF:                0000:00:1f.3
ID:                 8086:3a30 (ICH10 family SMBus)
subsystem ID:       1462:7522
PCI command:        0x0003
BAR4:               0x00000401
HOSTC (0x40):       0x01
Linux adapter:      /dev/i2c-0, "SMBus I801 adapter at 0400"
```

After the controlled SPD reads, side-effect-free reads of selected I/O
registers found:

```text
SMBus_PIN_CTL 0x40f: 0x07
```

For ICH10 `SMBus_PIN_CTL`, bit 2 releases SMBCLK to normal controller logic,
and bits 1:0 report the current DATA and CLK levels.  Thus `0x07` means clock
control released and both lines observed high in this running Linux state.
Intel ICH10 Specification Update 319974-017, documentation change 13,
corrects the published reset default of bit 2 to one.

`HST_STS` was deliberately not read through `/dev/port`, because its read has
I801 software-semaphore semantics.  Host command/address/data registers had
been changed by the immediately preceding Linux transactions and are not a
pristine firmware baseline.

## SPD address result

The repository's `scripts/read_spd_i2c.py` issued SMBus byte-data reads at
each standard SPD address.  Results:

| Address | Result |
|---:|---|
| `0x50` | DDR3 type `0x0b`; valid CRC `0xe5fc`; 4 GiB dual-rank x8 Corsair `CMX8GX3M2A1333C9` |
| `0x51` | `ENXIO` / no acknowledgement |
| `0x52` | same valid DDR3 SPD as `0x50` |
| `0x53` | `ENXIO` / no acknowledgement |
| `0x54` | same valid DDR3 SPD as `0x50` |
| `0x55..0x57` | `ENXIO` / no acknowledgement |

All three 256-byte payloads have SHA-256
`3d7d33481200d79ed5ec6467ac899df1196d984751bc8d8ae6755911e755bfd6`.
DMI reports the populated logical locators as `DIMM0`, `DIMM2`, and `DIMM4`,
each running at 1066 MT/s.  DMI names do not yet prove the physical
silkscreen-slot-to-address map.

## Consequence for B05 and B06A

The reference proves that the board design can expose valid DDR3 SPD devices
at `0x50`, `0x52`, and `0x54` after vendor initialization.  It does not prove
that the B05 test board had a DIMM at `0x50`, nor that its pre-DRAM pin state
was `0x07`.  B05 terminal `0xfa` remains consistent with an unclaimed cycle,
an SMBus device timeout, or another exact `DEV_ERR` cause.

B06A therefore isolates the next experiment: capture the pre-write pin value,
write only documented `SMBCLK_CTL=1`, verify both lines high, then perform one
bounded type-byte transaction at each address `0x50..0x57`.  Complete SPD
reads, CRC validation, slot mapping, IMC, QPI, and DDR training remain outside
B06A.
